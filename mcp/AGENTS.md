# MCP guidance

- Each tool group lives in its feature module (`src/watchlist.rs`, `src/nutrition/foods.rs`, ...) as a `#[tool_router(router = ..., vis = "pub(crate)")]` impl beside its request types and descriptions; register the router in `OpenHomeTools::new`. Contract tests mirror that: one integration-test file per feature in `tests/`, sharing `tests/common/mod.rs`. Keep every file under the 20,000-byte commit guard.

- Watchlist tools add, list, read, correct status/dates and remove movie/whole-series plans through authenticated Axum. Require explicit owner targeting; missing owners return API clarification, never a guessed destination. Reuse request IDs/arguments after uncertain additions. Reads are read-only, deduplicated additions non-destructive/idempotent, corrections/removals destructive/idempotent. After an uncertain correction, read the explicit owner/entry destination before retrying. Axum owns completion defaults, date consistency and filters. See `../docs/watchlists.md`.

- Wishlist tools may create named lists and add, read, edit or delete items; forward typed authenticated API operations unchanged. Destination resolution, validation and deduplication belong in Axum. Reads stay read-only; annotate additive writes as non-destructive. Deduplicated additions and item edits/deletes are idempotent; edits/deletes are destructive. See `../docs/wishlists.md`.

- Important Date tools list, read, add, update and delete household-shared dates through authenticated Axum. Tags are explicit Household User IDs, never inferred; `person_ids` is required on addition, even when empty. Reuse request IDs/arguments after uncertain additions. Axum owns all day arithmetic. See `../docs/important-dates.md`.

- Food tools (`search_foods`, `food`) are read-only forwards of `/api/nutrition/foods`; Axum owns the Food database import, name search, units and the `food_database_unavailable` state. Keep the global instructions' density and waste conversions (millilitres and gross weights to edible grams) in step with the API's fields.

- Meal Log tools (`log_meal`, `meal_logs`, `update_meal_log`, `delete_meal_log`, `nutrition_day`) forward `/api/nutrition/meal-logs` and `/api/nutrition/days/{day}` unchanged. Axum owns Copenhagen days, Portion snapshots, totals and `request_id` deduplication. Logging is non-destructive and idempotent; corrections and deletions are destructive and idempotent. Keep the global instructions on explicit eaten-at times, splitting dishes into Foods, attaching the user's photo as base64 and reusing `request_id` on retries in step with the API. `log_meal`/`update_meal_log` carry base64 photos of up to 10 MB, so the endpoint accepts bodies up to `MAX_REQUEST_BODY_BYTES` (rmcp defaults to 4 MiB).

- Product tools (`lookup_product`, `link_product`) forward `/api/nutrition/products` unchanged. Axum owns barcode validation, the Open Food Facts read (fields, User-Agent, timeout, byte cap, no retries), label normalisation, suggested Foods and `request_id` deduplication. Lookup is read-only and open-world; linking is non-destructive, idempotent and open-world. `log_meal`/`update_meal_log` Portions take `food_id` or a linked `barcode`, plus optional per-100 g `estimates`. Keep the global instructions' barcode workflow (lookup, link once to the closest Food, log by barcode, Open Food Facts credit) in step with the API.
- Meal tools (`meals`, `save_meal`, `update_meal`, `delete_meal`) forward `/api/nutrition/meals` unchanged; `log_meal` takes either `portions` or a Meal name in `meal` with optional `overrides` (grams by `food_id` or `barcode`). Axum owns case-insensitive names, item checks, fresh snapshots at log time, `meal_needs_update` and `request_id` deduplication. Listing is read-only; saving is non-destructive and idempotent; updates and deletions are destructive and idempotent. Keep the global instructions (save only when the user names a Meal, offer to save a repeated meal, log known Meals by name without photo analysis) in step with the API.

- Supplement tools (`supplements`, `add_supplement`, `update_supplement`, `delete_supplement`) forward `/api/nutrition/supplements` unchanged; `log_meal`, `update_meal_log`, `save_meal` and `update_meal` take `supplement_doses` (`supplement_id`, `doses`) and `log_meal` overrides may give `{supplement_id, doses}`. Axum owns parameter keys, unit conversion, required forms (vitamin A, folate, niacin), dose snapshots, the food/supplement split and `request_id` deduplication. Listing is read-only; adding is non-destructive and idempotent; updates and deletions are destructive and idempotent. Keep the global instructions (protein powder is a Product; register from the label once; forms for supplement-only Upper Limits; doses beside Portions or as a Meal) in step with the API.

- `nutrition_summary` is a read-only forward of `/api/nutrition/summary` (`from`, `to`, `aggregation` day, week or month). Axum owns the 365-day limit, ISO weeks, partial edge periods, logged and missing days, means and weekly rates. Like `nutrition_day`, its first read of a past week stores that week's target record (ADR 0014), which is internal memoisation, so it keeps `read_only_hint`. Axum also owns the micronutrient coverage (means per logged day, Upper Limit days, cut down windows and the Lasting Shortfall rule). Keep the global instructions on missing days, the goal rate and micronutrient coverage in step with the API.

- `search_cards` is a read-only, open-world forward of `GET /api/binder/cards?card_code=` returning every variant of a Card Code; Axum owns Card Code validation, the OPTCG read (origin, timeout, byte cap, no redirects), image storage and `card_data_unavailable`. Keep the global instructions on empty results and outages in step with the API. See `../docs/binder.md`.

- `add_binder_entry` (non-destructive, idempotent through `request_id`, open-world because a first lookup asks the catalogue) and `binder_entries` (read-only) forward `POST`/`GET /api/binder/entries` unchanged. Axum owns owner clarification (`binder_destination_required`), Card lookup and storage, `card_not_listed`, quantity merging, receipts and Card Code ordering. The global instructions carry the photo workflow (read codes, normal or parallel, `search_cards`, ask once when ambiguous, `ja` only for visibly Japanese cards, report unlisted cards, explicit owner, reuse `request_id`, never store the photo); keep them in step with the API.

- `update_binder_entry` and `delete_binder_entry` (destructive, idempotent) forward `PATCH`/`DELETE /api/household-users/{owner_id}/binder/entries/{id}` unchanged. The update's `quantity`, `language` and `note` use `Patch`, so an omitted field is kept and only a null note clears. Axum owns the validation, the language-collision 409 and the 404 for a wrong owner or repeated delete.

- Read `../docs/training-context.md` before changing training tools or their contracts.
- Keep training tools read-only: each call makes one authenticated API GET and passes its JSON unchanged. Add an API endpoint before adding a tool that needs new interpretation; database access and domain rules belong in the API.
- Percent-encode path arguments, reject literal `.` and `..` segments, and keep API redirects disabled so requests stay on the intended endpoint.
