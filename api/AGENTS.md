# API guidance

- Keep HTTP handlers thin and domain logic in `src/services/`.
- For training reads, read `../docs/training-context.md`; the API owns dates, units, source resolution, freshness and coverage.
- For NOOP ingestion, read `../docs/noop/PUSH_PROTOCOL.md` and `../docs/noop/DATA_MODEL.md`. Keep its database, migrations and bearer token separate from the main API's.
- Use SQLx compile-time query macros for the main database and runtime queries for NOOP: compile-time macros only check `DATABASE_URL`. Refresh `api/.sqlx` with `just api-sqlx-prepare` after changing checked queries.
- The Food database (`food.db`, ADR 0013) is rebuildable reference data imported from the pinned DTU workbook in `services/nutrition/food_database`; it has its own `food_migrations/` and runtime queries, and nothing the user creates belongs in it. Name nutrient values by the keys and units in `services/nutrition/parameters.rs`; null is unknown, never zero.
- Meal Logs (`services/nutrition/meal_logs`) live in `app.db`: each Portion copies every known per-100 g value with its source (`food`, `label`, `estimate`) when it is logged (ADR 0012), so past Meal Logs and Nutrition Days never read the live Food database. A Meal Log's day is the Copenhagen calendar day of its time (`training::calendar`).
- Products (`services/nutrition/products`, `open_food_facts`) live in `app.db` with their label values per 100 g, NOVA Class and linked FoodID. Open Food Facts reads ask only for `FIELDS`, send the app's `USER_AGENT` (never an email or person), and use a short timeout, a byte cap and no retries; every failure maps to `open_food_facts_unavailable` without upstream text. Normalise labels into the vocabulary (OFF `_100g` masses are grams; complete kJ/kcal and salt/sodium from each other). A lookup previews without storing; a stored barcode is answered without calling OFF. A Product Portion snapshots label values first, then the linked Food, then agent estimates for keys neither has.
- Meals (`services/nutrition/meals`) live in `app.db` and hold references, never values: ordered Food (`food_id`, with the names and dataset version it was saved with) and linked Product (barcode) items with grams, under a name unique case-insensitively (`name_key`, Unicode-lowercased). Saving checks every item against the current Food database and linked Products. `log_meal` with `meal` copies the items as Portions with fresh snapshots (overrides replace an item's grams by its `food_id` or `barcode`) and records `meal_name` on the Meal Log; a Food the current dataset lacks or names differently is `meal_needs_update` (409) until the Meal is updated. Editing or deleting a Meal never touches Meal Logs. Meals also hold Supplement Doses (`meal_supplement_doses`, by `supplement_id`); a Supplement a Meal takes cannot be deleted.
- Supplements (`services/nutrition/supplements`) live in `app.db` with per-dose amounts: parameter amounts keyed and united as in the vocabulary (label g/mg/µg converted; kcal/kJ completed from each other), with a required `form` for `vitamin_a`, `folate`, `niacin_equivalent` and `niacin` (`FORMS`) so supplement-only Upper Limits can find their share, and named compounds (g, mg, µg) for anything without a parameter. A Supplement Dose in a Meal Log copies the per-dose amounts and compounds (`meal_log_supplement_doses`, `meal_log_dose_amounts`, `meal_log_dose_compounds`), so Supplement edits never change past days. Totals add Portions and doses; `intake::Intake` keeps the food share, supplement share and per-form supplement shares apart and adds up across days, and `intake::Compounds` sums compounds taken. Protein powder is a Product, never a Supplement.
- Targets (`services/nutrition/targets`, `goals`, ADR 0014): Trend Weight, Estimated Expenditure, the weekly Calorie Target and the Macro Targets are computed by `targets::plan` for any range of days with one read of each input, and appear on the Nutrition Day. Each ISO week's expenditure and BMR are stored in `nutrition_weeks` on the first read of any of its days (only for weeks starting on or before today) and never updated. The Nutrition Goal history (`nutrition_goals`) takes effect from the Copenhagen day it is set. Targets need the Profile's height, sex (`male` or `female`) and birth date, and a Body Weight on or before the day; otherwise they report what is missing and nothing is guessed.
- The shared AVIF encoder (`services/avif_encoder`) turns JPEG or PNG bytes into AVIF bytes and dimensions for any feature that stores images, and knows nothing of storage. It decodes within the 12,000 px and 256 MiB limits, converts embedded RGB/gray ICC profiles to sRGB before stripping them, encodes with libavif's aom encoder only (one thread) and runs one encode at a time across the whole process on a blocking worker. Callers pass the speed, quality and target long sides, and map its errors to their own (`avif_encoder/native.rs` owns the narrowly scoped native allocations, and sets matching CICP before RGB-to-YUV conversion). libavif/libaom build from vendored C with CMake: devenv provides cmake and yasm, the Dockerfile cmake, nasm and the cross C++ compilers, and `cmake/aarch64-linux-gnu.cmake` keeps aom's NEON code in arm64 cross builds.
- Meal photos (`services/nutrition/meal_photos`) use that encoder at speed 8 and quality 60, at most 1,600 px plus a 400 px thumbnail, and store the files in `meal-photos/` beside `app.db`; originals and metadata are never stored. Encode before writing anything, store files before the row that references them, and remove files when a write fails or a photo is replaced or deleted. `meal_photos.rs` documents who owns the files at each stage and the cancellation and crash windows that can leave unreferenced files. Only the photo routes raise the body limit (`PHOTO_BODY_LIMIT`).
- Cards (`services/cards`, ADR 0017, `../docs/binder.md`) are stored per catalogue variant (`cards`, with the AVIF image as a BLOB written in the same transaction) the first time a Card Code is searched; later reads never touch the catalogue. `services/optcg` is the only code that talks to optcgapi.com: fixed origin, short timeout, byte caps, no redirects, image URLs rebuilt from the origin, and every failure is `card_data_unavailable` without upstream text. Tests and the preview use loopback stand-ins, never the live volunteer-run service. Parse Card Codes with `CardCode::parse` at the boundary. Card Value is `services/card_value` (pure conversion, integer cents, rounded once) over ECB rates that `services/exchange_rates` stores from `services/ecb` (the full history file when the stored rates do not reach the oldest stored price, else the daily file); a failed refresh writes nothing, and tests and the preview serve the ECB file from loopback, never the live bank (`../docs/binder-values.md`).
- Keep applied migrations unchanged; add migrations to the appropriate database's migration directory.
- For PATCH requests, absent fields preserve values and explicit `null` clears nullable fields. Map unique violations to conflicts.
- When backing up or restoring NOOP, preserve the whole database, including receiver state, health rows, batch acknowledgements and staged replacements; use a stopped API or SQLite's online backup mechanism.
